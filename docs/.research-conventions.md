# OSS conventions research — what makes an agentic-tool repo look adoptable

Survey date: 2026-09-02. Repos read at HEAD via `gh api repos/{owner}/{repo}/readme` and
`gh api repos/{owner}/{repo}/contents/...` with `Accept: application/vnd.github.raw`.

**Repos surveyed:** `github/spec-kit`, `Aider-AI/aider`, `langchain-ai/langgraph`,
`OpenHands/OpenHands` (was `All-Hands-AI/OpenHands`), `anthropics/claude-code`,
`simonw/llm`, `astral-sh/uv`, `BerriAI/litellm`, `sst/opencode`.

**Headline for drydock:** the closest structural analogue is `github/spec-kit` (markdown
contracts + small Python CLI + agent slash commands), and the closest *governance* analogue
is `simonw/llm` (one maintainer, near-zero ceremony). Copy spec-kit's README shape and
llm's community-file footprint. Do not copy litellm or langgraph — their weight exists to
solve reviewer-scaling and commercial-support problems drydock does not have.

---

## 1. README anatomy that works

### The universal first screen

Every single repo surveyed uses the same four-block hero, in the same order, and all of them
write it in **raw HTML** (`<div align="center">`, `<p align="center">`) because Markdown
cannot center:

1. **Logo** — centered image, 200–340px wide. spec-kit uses a 200×200 webp; OpenHands a
   340px png; opencode and langgraph use a `<picture>` with `prefers-color-scheme` dark/light
   sources. The `<picture>` trick is worth copying — a single-color logo that inverts is
   cheap and looks deliberate.
2. **Name + tagline** — `<h1>` name, then an `<h3><em>` one-liner. spec-kit:
   *"Define what to build before building it — with any AI coding agent."*
   OpenHands: *"The self-hosted developer control center for coding agents and automations."*
   opencode: *"The open source AI coding agent."* langgraph:
   *"Low-level orchestration framework for building stateful agents."*
3. **Badge row** — 3–6 badges, centered, one line.
4. **The demo artifact** — this is the differentiator, see below.

Three repos also add a **nav link row** immediately under the badges
(`Quickstart | Docs | Self-Hosting | Slack` in OpenHands). It costs one line and converts
the hero into a table of contents for people who already know what the tool is.

### How they demo the tool in the first screen

This is the single highest-leverage decision and the survey splits cleanly:

| Repo | First-screen demo | Notes |
|---|---|---|
| `Aider-AI/aider` | **Animated SVG screencast** (`aider.chat/assets/screencast.svg`) | SVG, not GIF — sharp at any zoom, tiny, no autoplay jank. Best-in-class. |
| `OpenHands/OpenHands` | Full-width product screenshot (`automation-preview.png`) | GUI product, so a screenshot is the honest artifact. |
| `sst/opencode` | Full-width TUI screenshot, hyperlinked to the site | |
| `astral-sh/uv` | **A benchmark bar chart** as the hero image | Their whole pitch is speed, so the chart *is* the demo. Note: the pitch determines the artifact. |
| `github/spec-kit` | No image — a numbered **workflow list** of the slash commands, plus a 3-line install block | Their product is a *process*, so they show the process. |
| `langchain-ai/langgraph` | `pip install -U langgraph` in a fenced block, three lines in | |
| `simonw/llm` | Badges → one paragraph → a **YouTube link** with a written-notes link | |

**Rule extracted:** show the artifact that *is* the product. drydock's product is a queue that
moves specs through states while you are not watching, plus a board that shows it. That means
**two** artifacts: an animated terminal recording of the orchestrator loop ticking (asciinema →
SVG via `svg-term-cli`, aider-style, so it survives GitHub's image proxy and dark mode), and a
static screenshot of the board. Put the terminal SVG in the hero; put the board screenshot
next to the board section further down. A GIF is the fallback if the SVG route is fiddly, but
GIFs are heavy and blurry on retina.

### Section order

Convergent order across the set, with a hard rule: **install + first command land above the
fold on a laptop, or within one scroll.**

- spec-kit: TOC → *What is SDD* → quickstarts (3 of them) → video → community → integrations →
  CLI reference → extensibility → philosophy → phases → prerequisites → support → license.
- langgraph: tagline → install → *Why use X* (5 bullets, each a doc link) → ecosystem → docs →
  resources → acknowledgements.
- OpenHands: hero → prose paragraph → **feature table** (2-col, link + one-line description) →
  Quickstart with 3 numbered install options → docs links.
- llm: badges → one dense sentence naming the models → "With LLM you can:" bullet list →
  Quick start with 4 install variants.

The recurring skeleton is: **what it is → why you'd want it → install → first run → how it
works → everything else.** Nobody leads with architecture. spec-kit puts its "Core Philosophy"
section roughly 70% of the way down; langgraph never explains its internals in the README at
all and links out.

### Length

Two viable strategies, and picking one matters:

- **Long single README** (spec-kit ≈ 400 lines with a TOC, litellm similar). Works only if you
  add a TOC. spec-kit's TOC is hand-maintained with emoji-prefixed anchors.
- **Short README, everything linked out** (langgraph ≈ 60 lines, uv ≈ 90, opencode ≈ 80). The
  README is a landing page; docs live on a site or in `docs/`.

For drydock, **short-to-medium (150–220 lines), no TOC, no emoji headers.** A TOC in a README
under ~250 lines is noise. drydock already has real reference docs in `contracts/`, so the
README's job is to sell + get someone to their first tick, then hand off.

### How they explain architecture

- Nobody uses a Mermaid diagram in the README. (Notable — Mermaid renders natively on GitHub
  and still nobody does it.) They use **ASCII-free prose + tables** instead.
- spec-kit's best architecture device is a **priority-ordered table** for its template
  resolution stack (`Priority | Component Type | Location`, arrows ⬆1…⬇4). It explains a
  layered lookup in five rows where three paragraphs would have failed.
- OpenHands' device is a **two-column feature table** where the left cell is a bolded doc link
  and the right cell is one line of what it does. Scannable, and every row is a click.
- langgraph's device is a **bulleted list where every bullet's bold lead-in is a doc link** —
  *"**[Durable execution](...)** — Build agents that persist through failures…"*.

**Rule extracted:** architecture in a README is explained as a *table of moving parts*, not a
diagram and not prose. Save the diagram for `docs/`. For drydock this is a natural fit: a
table of `contracts/*.md` (the contract, what it governs, who reads it) and a table of the
queue directories (`specs/inbox` → `specs/active` → `specs/blocked` → `archive`,
`deliverables/`) does more work than any picture. A Mermaid state diagram of the queue belongs
in `docs/ARCHITECTURE.md`, linked from the README.

Two more devices worth stealing:

- **GitHub alert callouts** (`> [!NOTE]`, `> [!TIP]`, `> [!WARNING]`) are used by spec-kit,
  langgraph, OpenHands, and opencode. OpenHands uses `[!WARNING]` twice to flag that an
  install option gives the agent full filesystem access — exactly the right register for
  drydock's "the orchestrator writes to your repo and runs agents unattended" warning.
- **Multiple labeled install paths** (OpenHands "Option 1 / 2 / 3", llm's four package
  managers). drydock has at least two entry modes (clone-and-run vs. install the plugin),
  and labeling them as options prevents the reader from guessing.

```
# sst/opencode — flat-square, 3 badges
https://img.shields.io/discord/1391832426048651334?style=flat-square&label=discord
https://img.shields.io/npm/v/opencode-ai?style=flat-square
https://img.shields.io/github/actions/workflow/status/anomalyco/opencode/publish.yml?style=flat-square&branch=dev
```

Findings:

- **Style consistency matters more than which style.** Each repo picks one (`flat-square`,
  `for-the-badge`, or default flat) and applies it to every badge. Mixed styles read as
  accreted rather than designed. litellm is the counterexample — 7 badges in 3 styles
  including a "Y Combinator W23" badge — and it looks like a startup landing page, not a tool.
- **The load-bearing four are: release/version, license, CI status, docs.** Everything past
  that is social proof (stars, Discord, downloads).
- The **`?label=changelog` release badge** (llm) is a genuinely good idea most repos miss: the
  version number is also the link to what changed.
- `style=social` stars badges are used by spec-kit and litellm; they visually clash with flat
  badges. Skip.
- aider's badges are **generated by `cog`** from `scripts/homepage.py` inside an HTML comment
  block in the README — the badges carry live numbers (6.8M installs, 15B tokens/week, "88%
  Singularity" = share of the last release written by aider itself). Over-engineered for a new
  project, but the *idea* of a vanity metric that is actually about the product is strong;
  drydock's equivalent would be a spec-throughput number, and it's premature.

**Recommended for drydock (4 badges, `flat-square`, one row):**

```markdown
[![License: MIT](https://img.shields.io/github/license/phspagiari/drydock?style=flat-square)](LICENSE)
[![CI](https://img.shields.io/github/actions/workflow/status/phspagiari/drydock/ci.yml?branch=main&style=flat-square&label=ci)](https://github.com/phspagiari/drydock/actions/workflows/ci.yml)
[![Release](https://img.shields.io/github/v/release/phspagiari/drydock?style=flat-square&label=changelog)](https://github.com/phspagiari/drydock/releases)
[![Claude Code](https://img.shields.io/badge/built%20for-Claude%20Code-d97757?style=flat-square)](https://claude.com/claude-code)
```

Add the release badge only once there is a tag; a badge pointing at "no releases" is worse
than no badge. The `built for Claude Code` custom badge is the one piece of positioning a
badge can do here — it answers "what does this plug into" before any prose does.

## 3. Community files — what a solo maintainer actually needs

Verified state across the surveyed repos:

| File | spec-kit | aider | langgraph | OpenHands | claude-code | llm | litellm |
|---|---|---|---|---|---|---|---|
| `CONTRIBUTING.md` | 292 lines | 241 lines | **404** (off-repo) | **404** | **404** | **404** (66-line `docs/contributing.md`) | 346 lines |
| `SECURITY.md` | GitHub boilerplate | **404** | **404** | **404** | HackerOne link | **404** | `security.md`, bounty table |
| `CODE_OF_CONDUCT.md` | Contributor Covenant | **404** | **404** | **404** | **404** | **404** | **404** |
| Issue templates | 6 YAML forms + `config.yml` | 1 YAML form | 2 + `config.yml` | 2 YAML | 4 + `config.yml` | **none** | 2 + `config.yml` |
| PR template | yes (+ AI disclosure) | **404** | yes, heavy | yes, `HUMAN:`/`AGENT:` split | **404** | **404** | very heavy |
| `CODEOWNERS` | yes | no | — | — | — | no | yes |
| `FUNDING.yml` | no | no | — | — | — | yes | yes |
| `dependabot.yml` | yes | no | yes | yes | — | yes | yes |

**Six of seven repos ship no CODE_OF_CONDUCT**, including two VC-backed ones. Only litellm
requires a CLA (via cla-assistant.io), and it does so because it sells an enterprise tier.

### CONTRIBUTING.md structure, from the two that are worth copying

- **aider** (`CONTRIBUTING.md`, 241 lines) — H2s: `Bug Reports and Feature Requests`,
  `LLM Benchmark Results`, `Pull Requests`, `Licensing`, `Setting up a Development
  Environment`, `Coding Standards`. Almost entirely dev-setup. Its best move is stating a
  *negative* convention explicitly (**"No Type Hints"**) — contributors guess wrong about house
  style unless you write the anti-rules down.
- **simonw/llm** (`docs/contributing.md`, 66 lines) — H2s: `Updating recorded HTTP API
  interactions and associated snapshots`, `Debugging tricks`, `Documentation`,
  `Release process`. Sixty-six lines, zero governance prose, includes the release process so
  future-Simon doesn't have to remember it. This is the right size.
- **spec-kit** is the one with a genuinely novel section for an agentic repo: **`AI
  contributions in Spec Kit`**, plus a branch-naming convention (`<type>/<number>-<slug>`) and
  a mandatory AI-disclosure checkbox in the PR template. For a repo whose entire premise is
  agent-written code, having a stated position on agent-written *contributions* is coherent
  rather than performative.

### Recommendation for drydock

**Ship (5 files, ~150 lines total):**

1. **`CONTRIBUTING.md`, ~60–80 lines.** Sections: `Running the board locally`,
   `Testing a contract change` (the hard part — how do you validate a markdown contract?),
   `House conventions`, `Release process`. Include the negative rules: no dependencies in
   `board/server.py` beyond stdlib (already stated in the module docstring, worth promoting),
   contracts stay in Markdown, HTML renders are gitignored and never committed.
2. **`SECURITY.md`, ~10 lines.** Enable GitHub private vulnerability reporting and say so in
   one paragraph. drydock genuinely has a security surface worth naming: the board binds
   127.0.0.1 and serves arbitrary file contents from the repo it is pointed at, and the
   orchestrator runs agents with elevated permissions unattended. A short SECURITY.md that
   states the threat model in three sentences is more useful than any bounty table.
3. **`.github/ISSUE_TEMPLATE/bug_report.yml`** — YAML form. Fields: what you ran, the spec
   state at the time (`inbox`/`active`/`blocked`), Claude Code version, orchestrator log
   excerpt. The structured fields are the point; they save the triage round-trip.
4. **`.github/ISSUE_TEMPLATE/config.yml`** with `blank_issues_enabled: false`, routing
   questions to Discussions. Cheapest possible support-load deflection.
5. **`.github/PULL_REQUEST_TEMPLATE.md`, ~8 lines.** "What changed / How you verified it /
   Which contract this touches, if any." Given drydock's premise, add spec-kit's AI-disclosure
   line — it is on-brand rather than bureaucratic here.

**Skip:** `CODE_OF_CONDUCT.md` (a moderation promise with no moderation process behind it),
`CODEOWNERS` (meaningless with one maintainer), CLA, `SUPPORT.md`, feature-request template
(feature requests are Discussions), any bounty or severity taxonomy.

**Add `dependabot.yml` only for `github-actions`** — drydock's Python is stdlib-only, so the
`pip` ecosystem has nothing to update. Action-version bumps are the real value and they arrive
as a handful of PRs a year.

## 4. CI for a mostly-markdown + small-Python repo

### What the survey found

- **Markdown CI is nearly nonexistent.** Of nine repos, exactly one (`github/spec-kit`,
  `.github/workflows/lint.yml`) runs `markdownlint-cli2`, alongside a `git diff --check`
  whitespace check and `shellcheck` on `*.sh`. **Nobody** runs lychee, markdown-link-check,
  vale, or a TOC generator. That is a strong negative signal: doc-heavy projects have tried
  link-checking and abandoned it, because external URLs rate-limit and fail CI for reasons
  unrelated to the PR.
- **The one clever markdown-adjacent check** is `simonw/llm`'s `cog`: `test.yml` runs
  `cog --check` to fail if the code examples embedded in `docs/**/*.md` have drifted from real
  CLI output, and `cog.yml` auto-regenerates and commits the fix back to the PR branch. This
  is the pattern to remember — not "are the links alive" but **"are the documented commands
  still true."**
- **Modern hygiene is near-universal:** top-level `permissions: contents: read`, a
  `concurrency` group with `cancel-in-progress: true`, and OIDC trusted publishing
  (`pypa/gh-action-pypi-publish` with `id-token: write`, gated by a GitHub `environment`).
  Present in spec-kit, langgraph, uv, llm, litellm; absent in aider, which still uses a raw
  twine token — the older pattern, don't copy it.
- **Matrix width tracks package surface area, not doc volume.** llm runs 15 cells
  (3 OS × 5 Python) because it's a plugin ecosystem; spec-kit runs 6; langgraph up to 35 via
  reusable workflows fanned out per sub-package and gated by `dorny/paths-filter`.
- **langgraph's `ci_success` fan-in job** is worth knowing: a final job that ORs failure across
  the whole matrix, registered as the single required check in branch protection. It means you
  can change the matrix without touching branch-protection settings. Useful once you have more
  than ~3 jobs; overkill below that.
- **litellm is the cautionary tale.** Dozens of workflows, 17 named test shards whose `name:`
  strings are load-bearing because branch protection references them by exact string, and
  custom Python "budget gate" scripts that ratchet lint/type metrics against the base branch.
  This is what CI looks like after it metastasizes on a team; a solo maintainer inherits all
  the maintenance and none of the benefit.

### Recommended CI for drydock

Two workflows. Anything wider gets disabled within a month.

**`.github/workflows/ci.yml`** — `on: [pull_request, push to main]`, top-level
`permissions: contents: read`, `concurrency: ${{ github.workflow }}-${{ github.ref }}` with
`cancel-in-progress: true`. Three small jobs, all `ubuntu-latest`, **no matrix**:

- `python` — `astral-sh/setup-uv`, then `uv run ruff check .`, `uv run ruff format --check .`,
  `uv run pytest` (drydock already has `board/tests/`). One tool, two checks; skip mypy and
  black — ruff covers what black + flake8 + isort used to need three tools for, and a
  ~350-line stdlib HTTP server does not earn a type-check gate. Single Python version, pinned
  in `pyproject.toml` / `.python-version`.
- `markdown` — `DavidAnson/markdownlint-cli2-action` over `**/*.md`, with a `.markdownlint.jsonc`
  that disables MD013 (line length) and MD033 (inline HTML, which the hero section needs).
  Configure it up front or the first run will be a wall of false positives.
- `actionlint` — catches malformed workflow YAML before it burns a run. Near-zero cost.

**`.github/workflows/release.yml`** — `on: push: tags: ['v*']`, `permissions: contents: write`,
one step: `gh release create ${{ github.ref_name }} --generate-notes`. GitHub's auto-generated
changelog is free and adequate. drydock is cloned, not `pip install`ed, so there is no PyPI
story to build; if that changes, copy `simonw/llm`'s `publish.yml` (OIDC, `environment: release`)
rather than twine tokens.

**Explicitly skip:** link checkers (the survey's clearest negative finding), spellcheck/vale
(needs an allowlist nobody maintains solo), CodeQL and OSSF Scorecard (Dependabot alerts cover
the real risk for free), test matrices, and coverage gates.

**The one custom check worth considering later**, in the spirit of llm's `cog`: a script that
asserts every directory and file path named in `contracts/*.md` and `README.md` actually
exists in the tree. drydock's contracts are load-bearing prose that references real paths, and
a stale path in `ORCHESTRATOR.md` is a genuine bug the way a dead external link is not. That
is ~20 lines of Python and it checks something true about *this* project. Don't ship it in v1;
ship it the first time a contract goes stale.

## 5. Naming and tagline patterns

Every tagline in the survey is one line, under ~12 words, and follows one of three shapes:

**A. Category + differentiator** (the most common)
- langgraph: "Low-level orchestration framework for building stateful agents."
- uv: "An extremely fast Python package and project manager, written in Rust."
- opencode: "The open source AI coding agent."
- OpenHands: "The self-hosted developer control center for coding agents and automations."

**B. Imperative / promise**
- spec-kit: "Define what to build before building it — with any AI coding agent."
- aider: "AI Pair Programming in Your Terminal" (this one is the `<h1>` itself — the *tagline*
  is the heading and "aider" is only in the logo. Bold, and it works because the tagline is
  more searchable than the name.)

**C. Capability list compressed into a sentence**
- llm: "A CLI tool and Python library for interacting with OpenAI, Anthropic's Claude, … and
  dozens of other Large Language Models."

Structural observations:

- **The em dash is doing real work.** spec-kit and several others use `X — with Y` to attach
  the compatibility claim without a second sentence. Copy this.
- **Several repos carry a second, longer line under the tagline** (spec-kit's bolded paragraph;
  OpenHands' "Run OpenHands, Claude Code, Codex, Gemini, or any ACP-compatible agent…").
  The pattern is *tagline for the skim, one sentence for the squint*.
- **Nobody explains the metaphor in the tagline.** If the name is metaphorical (drydock,
  opencode, aider), the tagline states the literal function and the metaphor is left to pay off
  later or not at all. This matters: "ships are built and inspected in the dock, launched only
  when ready" is a great *positioning* line and a bad *tagline*, because it does not say what
  the software does.

### Tagline options for drydock

Ranked, with what each optimizes for:

1. **"Specs in, pull requests out — an agentic pipeline for Claude Code."**
   Best all-rounder. States the I/O contract in four words, names the platform, and the
   pipeline noun sets expectations of unattendedness. Searchable on "Claude Code" + "pipeline".

2. **"Ships code, not drafts — a spec-driven agent pipeline where review happens before the PR."**
   Leads with the actual differentiator (pre-PR adversarial review) and lands the dock
   metaphor in two words. Slightly long; the em-dash clause carries it.

3. **"A git repo as the queue. Worktrees as the workshop. No PR until it's ready."**
   Three-beat, most distinctive, most memorable. Weakest on search terms — doesn't contain
   "Claude Code" or "agent". Would work as the *second* line under a plainer tagline.

4. **"Spec-driven agent orchestration for Claude Code — reviewed in the dock, launched when ready."**
   Safest. Category + differentiator + metaphor payoff. Slightly generic in its first half;
   "orchestration" is a crowded word in 2026.

5. **"Queue specs, dispatch agents, review before the PR exists."**
   Imperative triple. Punchy but reads as a feature list rather than a positioning line.

**Recommendation:** tagline `#1` as the `<h3>`, then the metaphor as the bolded sentence
beneath it — that's exactly the two-tier structure spec-kit and OpenHands use:

> ### Specs in, pull requests out — an agentic pipeline for Claude Code.
>
> **Interactive sessions produce specs. A git repo is the queue. An orchestrator dispatches
> executor agents into worktrees, and adversarial review happens before any PR exists — ships
> are built and inspected in the dock, and launched only when ready.**

## 6. Recommended README outline for drydock

Target ~180 lines. No table of contents. No emoji in headings (spec-kit's emoji headers are a
GitHub-house style that reads as noise outside it). Numbers below are rough line budgets.

**1. Hero (~20 lines, raw HTML, centered)**
Logo (a `<picture>` with dark/light variants — an anchor or a dock silhouette; even a
well-set wordmark beats no logo) → `<h1>drydock</h1>` → `<h3><em>` tagline #1 → bolded
metaphor sentence → badge row (the 4 from §2, `flat-square`) → nav row:
`Quickstart | How it works | Contracts | Board`.

**2. The demo (~5 lines)**
Full-width animated SVG of one orchestrator tick: a spec moving `inbox → active`, an executor
dispatched, the reviewer's verdict, the spec landing in `deliverables/`. Record with
asciinema, convert with `svg-term-cli`, commit under `docs/media/`. This is the single most
valuable asset in the whole README and worth doing properly before launch.

**3. What drydock is (~12 lines)**
Three or four sentences of prose, then the differentiator as a `> [!NOTE]` callout. The
sentence that has to land: *most agentic pipelines review code in the PR; drydock reviews it in
the worktree, and the PR only exists once the work has already survived review.* Anyone
evaluating this in fifteen seconds needs that one idea.

**4. Quickstart (~30 lines)**
Two labeled options, OpenHands-style:
- *Option 1 — clone and run* (`git clone`, `python3 board/server.py serve`, drop a spec in
  `specs/inbox/`, start the orchestrator loop). Lead with this: stdlib-only, no install step,
  which is a genuine selling point already stated in `board/server.py`'s docstring — say it
  out loud in the README.
- *Option 2 — install the Claude Code plugin* (`plugin/`), for using drydock's skills against
  an existing repo.

Include a `> [!WARNING]` on the orchestrator: it dispatches agents that write to your repo
unattended, and the board serves file contents from the repo it is pointed at over
`127.0.0.1`. OpenHands sets the precedent for stating this plainly in the quickstart rather
than burying it.

**5. How it works (~35 lines)**
Prose lead-in, then **two tables** (per §1's finding that architecture reads better as tables
than diagrams):

- *The queue* — `specs/inbox/` · `specs/active/<id>/` · `specs/blocked/` · `deliverables/` ·
  `archive/`, with one line each for what a spec being in that directory means and what moves
  it out. This is the state machine; a table is the honest rendering of it.
- *The contracts* — `ORCHESTRATOR.md` · `DISPATCH.md` · `REVIEWER.md` · `PRIORS.md` ·
  `PROPOSALS.md`, each row: what it governs, who reads it, when it is consulted. Link every
  filename. The fact that these are plain Markdown a human can edit is a feature — say so.

Then one short paragraph on the roles (orchestrator loop, executor agents in worktrees,
adversarial reviewer) and a link to `docs/ARCHITECTURE.md` for the Mermaid state diagram.

**6. The board (~10 lines)**
Screenshot, two sentences: reads queue state from disk on every request, no cache, no daemon,
no regeneration step; `python3 board/server.py serve --port 8642`. The "what you see is what
is on disk right now" line from the docstring is already good copy — promote it verbatim.

**7. Writing a spec (~15 lines)**
Point at `templates/spec-template.md` and list its section names (Context, Goal, Non-goals,
Constraints & blast radius, Requirements, Acceptance criteria, Escalation conditions,
Assumptions). Emphasize *executable acceptance criteria* — that is the contract that makes
autonomous execution safe, and it's the section a newcomer will under-fill. One worked
example under `examples/`, linked.

**8. Design principles (~15 lines)**
Four or five bullets, spec-kit's "Core Philosophy" slot in the ordering. Candidates: markdown
contracts over code (a human can edit the rules), git as the state machine (no database, no
daemon), stdlib only (clone and run), review before the PR exists, fail closed (the preflight
in `DISPATCH.md`). This section is what makes a reader trust the project rather than merely
understand it, and it's cheap.

**9. Prerequisites (~5 lines)** — Claude Code, Python 3.11+, git 2.x with worktree support, `gh`.

**10. Status (~5 lines)**
An honest maturity statement. Every surveyed project that is early says so; `OpenHands` ships a
`status-beta` badge. A `> [!NOTE]` saying what works today and what is still moving buys far
more goodwill than silence, and it pre-empts the issues you'd otherwise triage.

### Things to deliberately not do

- No TOC (README is too short to need one; a stale TOC is worse than none).
- No emoji section headers.
- No Mermaid in the README — it belongs in `docs/ARCHITECTURE.md`.
- No stars badge, no "star this repo" plea.
- No comparison table against other agentic tools. None of the nine repos does this; it ages
  badly and reads as defensive.
